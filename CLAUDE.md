# Nanotrace development guide

Nanotrace records CPU scopes, Blackwell HES kernel timestamps, and explicit
CUDA intra-kernel ranges into one clock-correlated v4 trace. The WebGPU viewer
renders those sources on a shared timeline.

## Repository layout

~~~text
nanotrace-cuda/
  include/nanotrace/
    nanotrace.cuh          Device instrumentation
    nanotrace_host.h       CUDA lane builders and session attachment
    nanotrace_hes.h        CUPTI HES collector
    nanotrace_session.h    CPU events, tracks, clocks, and v4 writer
  src/                     Host implementations
  examples/                Standalone trace producers and benchmarks
visualizer/
  src/                     WebGPU viewer and v4 parser
  public/                  Canonical committed v4 samples
  scripts/validate.ts      Format-agnostic parser/projection validator
docs/nanotrace.md          Nanotrace v4 binary format
~~~

## Build and validation

The standalone CUDA build requires CUDA 13.3, C++20, CMake 3.18 or newer,
Ninja, and an `sm_120a` GPU for CUDA examples.

~~~bash
cmake -S nanotrace-cuda -B build -GNinja \
  -DBUILD_EXAMPLES=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build
~~~

The viewer requires Node.js 26 and npm 11.

~~~bash
cd visualizer
npm ci
npm run build
for trace in public/*.nanotrace; do npm run validate -- "$trace"; done
~~~

Builds must complete without warnings. Do not suppress a warning when the API
has a direct non-deprecated equivalent.

## Canonical samples

Committed samples are generated by the real v4 C++ writer, never by a second
TypeScript encoder:

- `unified_trace.nanotrace`: three kernels, CPU scopes, CUPTI HES, and one
  expandable intra-kernel trace;
- `multistream_graph.nanotrace`: a captured CUDA graph whose kernels execute
  across two driver-selected execution streams;
- `cpu_hierarchy.nanotrace`: deterministic application-defined CPU parent and
  worker tracks;
- `tma_bandwidth_static_sm120a.nanotrace`: statically scheduled TMA transfers
  across 170 blocks;
- `tma_bandwidth_atomic_sm120a.nanotrace`: dynamically scheduled TMA transfers
  across 170 blocks.

Regenerate from the repository root after building the examples:

~~~bash
./build/examples/cpu_hierarchy_trace \
  visualizer/public/cpu_hierarchy.nanotrace
CUDA_VISIBLE_DEVICES=0 ./build/examples/unified_trace \
  visualizer/public/unified_trace.nanotrace
CUDA_VISIBLE_DEVICES=0 ./build/examples/multistream_graph_trace \
  visualizer/public/multistream_graph.nanotrace
CUDA_VISIBLE_DEVICES=0 ./build/examples/tma_bandwidth_bench_static 170 \
  visualizer/public/tma_bandwidth_static_sm120a.nanotrace
CUDA_VISIBLE_DEVICES=0 ./build/examples/tma_bandwidth_bench_atomic 170 \
  visualizer/public/tma_bandwidth_atomic_sm120a.nanotrace
~~~

HES examples must be the first CUDA users in their processes. Regenerated GPU
samples must come from the configured `sm_120a` build.

## Trace format and clocks

Nanotrace v4 is the only supported file format. It uses a 32-byte `NTRACE4`
header followed by optionally compressed chunks for the session, strings,
clocks, clock snapshots, tracks, events, arguments, and reusable event formats.
The authoritative layout is `docs/nanotrace.md`.

`CLOCK_MONOTONIC_RAW` is the session reference clock. CUPTI timestamps are
mapped into it with bracketing snapshots. Explicit device events use
`%globaltimer_lo`; `finish_lane()` records one full `%globaltimer` anchor after
the measured work. Post-processing reconstructs the low timestamps and then
maps them through the matching HES kernel event.

A lane capture must span less than one 32-bit `%globaltimer_lo` wrap. Device
rows and committed headers remain 16-byte aligned.

## GPU capture lifecycle

Construct `GpuTrace` before any CUDA runtime or driver operation creates a
context. After setup and warm-up, call `Begin()`, run the instrumented workload,
copy the device tensor into a `trace_writer`, and call `Write()`. `GpuTrace`
owns HES initialization, priming, clock snapshots, kernel matching, attachment,
shutdown, and unified serialization. Examples should not reproduce that
low-level sequence.

## CPU and track hierarchy

`CpuThreadContext` uses a fixed-capacity per-thread buffer and flushes it into
the session without copying events into a global vector. Give related tracks
serialized parent IDs with the constructor or `TraceSession::SetTrackParent()`.
The viewer treats this hierarchy as application-defined; it must not infer
parents from track names.

Overlapping root events on one CPU track are rendered in separate sublanes.
Event parent IDs are reserved for real event ownership and child expansion.

## Device instrumentation

Use compile-time trace, block, and track definitions from `nanotrace.cuh`.
Only controlling threads should enable a lane. Every enabled lane must call
`finish_lane()` after its final event.

`NANOTRACE_DISABLED` must preserve source compatibility while compiling all
device instrumentation away. Any new device API requires an equivalent
disabled stub. `NANOTRACE_NO_LOG` suppresses writer diagnostics, and
`NANOTRACE_WITH_MINIZ` enables deflate compression.

## Viewer invariants

- GPU rows sort above CPU rows.
- Multiple execution streams can collapse into one GPU row without changing
  the materialized event topology.
- Expanding a row changes visibility and Y offsets rather than rebuilding the
  trace or GPU buffers.
- Intra-kernel events remain children of one HES kernel and must lie within its
  interval after clock correlation.
- Nested or overlapping events use sublanes; they must never draw over one
  another on the same sublane.
- Sample validation is format- and application-agnostic. Do not special-case
  session names, kernel names, event labels, or expected sample counts.

## Generated files

Do not commit `visualizer/dist`, `visualizer/node_modules`,
`visualizer/.validate`, or CMake build directories. Canonical files directly
under `visualizer/public` are the only committed `.nanotrace` binaries.
